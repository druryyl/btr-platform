# 1. Request Summary

The change request assesses enabling visit data materialization directly from within the SM7 – Jadwal Kunjungan menu (`JadwalKunjunganForm`) in `btr.distrib`.

Referenced artifacts:

- ISSUE: `docs/issues/BTR-DISTR-SM7-VISIT-MATERIALIZE-ISSUE.md` (`BTR-DISTR-SM7-VISIT-MATERIALIZE-001`)
- DOMAIN: `docs/foundation/DOMAIN.md`
- FEATURE: `docs/features/visit-plan/feature.md`
- PRIOR IMPLEMENTATION PLAN: `docs/work/sales-route-materialization/implementation-plan.md`

## Objective

Evaluate the feasibility, scope, risks, and technical requirements of allowing operational supervisors to trigger visit plan materialization from inside `JadwalKunjunganForm` (SM7) for a selected salesperson and date, eliminating dependency on running an external console worker (`btr.visitplan.worker`) or dummy-saving the recurring route template in SM4.

---

# 2. Current State

## Existing Behavior

1. **Materialization Architecture:**
   - The Territory Execution Plan operates with a recurring route template (`BTR_SalesRute` / `BTR_SalesRuteItem`), a materialized base plan (`BTR_VisitPlan`), an exception overlay (`BTR_VisitPlanException`), and an effective plan dynamically resolved at query time by `EffectiveVisitPlanResolver`.
   - Materialization is executed by `IRegenerateVisitPlanWorker` (`RegenerateVisitPlanWorker` in `btr.application.SalesContext.VisitPlanAgg.UseCases`).
   - `RegenerateVisitPlanWorker` takes a `RegenerateVisitPlanRequest` (`SalesPersonId`, `FromDate`, `ToDate`, `AllowPast`, `TriggeredBy`). It resolves calendar dates to `HariRuteId` (`H11`–`H26`) via `IRuteCycleCalendar`, reads the template from `ISalesRuteDal` and `ISalesRuteItemDal`, deletes existing future rows via `IVisitPlanDal.DeleteFuture()`, and bulk-inserts new rows into `BTR_VisitPlan`.

2. **Current Triggers for Materialization:**
   - **SM4 Template Save:** In `SalesRuteWriter.Save()`, saving a route template automatically triggers `_regenerateVisitPlanWorker.Execute` with `SalesPersonId = model.SalesPersonId`, `FromDate = today`, `ToDate = null`, and `TriggeredBy = "TemplateSave"`.
   - **Background Worker:** `btr.visitplan.worker.exe` runs `WorkerRunCoordinator` calling `IMaintainVisitPlanHorizonWorker.Execute()` to regenerate all salesmen for the rolling horizon (default 90 days).
   - **SM7 Menu (`JadwalKunjunganForm`):** Only performs read queries via `RefreshPlans()`. When a salesperson and date are selected, it queries `_visitPlanDal.ListData()`, `_effectiveVisitPlanDal.ListEffectivePlan()`, and `_exceptionDal.ListData()`.

3. **Current Problem:**
   - In environments where `btr.visitplan.worker` is not scheduled or has not yet run, or when viewing a salesperson/date combination not yet materialized, SM7 shows an empty base grid and empty effective grid.
   - SM7 has no user controls (buttons or actions) to initiate materialization. The supervisor cannot resolve the blank schedule without leaving the application to run the console worker or opening SM4 to force a save on the route template.

## Existing Constraints

1. **Historical Immutability (Decision D5):**
   - Past materialized records (`VisitDate < today`) are immutable. They must never be deleted or regenerated by operational users. `RegenerateVisitPlanWorker` enforces `fromDate = max(today, request.FromDate)` unless `AllowPast == true`.
2. **Cycle Anchor and 14-Day Cycle (Decision D1):**
   - Dates are mapped to 12 slots (`H11`–`H26`) via `IRuteCycleCalendar` using `ROUTE_CYCLE_ANCHOR_DATE` (configured in `BTR_ParamSistem`).
3. **Sunday Exclusion (Decision D2):**
   - Sunday produces no materialized visit rows (`date.DayOfWeek == DayOfWeek.Sunday` is skipped).
4. **Exception Preservation (Layered Architecture):**
   - `BTR_VisitPlanException` rows (`Add`, `Remove`, `Replace`) are stored separately from `BTR_VisitPlan`.
   - Re-materializing `BTR_VisitPlan` replaces base template rows only; it does not touch `BTR_VisitPlanException`. The resolver overlays exceptions on top of whatever base plan rows exist.
5. **Authorization (Decision D8):**
   - SM7 is restricted to supervisor level and above (`LEADR`, `SFKTR`, `SYSAD`). Salespersons (`SALES`) cannot access SM7.
6. **Desktop DI Registration:**
   - `IRegenerateVisitPlanWorker` is already registered in `btr.distrib` via assembly scanning of `INunaServiceVoid<>` in `Program.cs`.

# 3. Gap Analysis

| ID | Severity | Gap |
|----|----------|-----|
| GAP-001 | CRITICAL | `JadwalKunjunganForm` has no UI trigger (button or menu item) to execute visit plan materialization. |
| GAP-002 | MAJOR | `JadwalKunjunganForm` does not inject `IRegenerateVisitPlanWorker` to call the materialization use case. |
| GAP-003 | MAJOR | Materialization scope ambiguity: The issue requests materializing for "the selected sales person and selected date". If only a single date is materialized (`FromDate = date, ToDate = date`), subsequent days remain unmaterialized, requiring repetitive clicks for future days. |
| GAP-004 | MINOR | Lack of user feedback in SM7 when materialization produces zero rows (e.g. Sunday or salesman has no customers assigned to that route slot). |

# 4. Open Questions

| ID | Question | Impact |
|----|----------|--------|
| OQ-001 | Should in-menu materialization generate only the single selected date (`FromDate = date, ToDate = date`) or the standard rolling horizon starting from the selected date (`FromDate = date, ToDate = null` / 90 days)? | Affects operational efficiency: Single-date materialization strictly matches the literal request but leaves future days blank; rolling horizon materialization aligns with the system horizon model and prevents repeated clicks. |
| OQ-002 | Should materialization in SM7 be strictly on-demand via an explicit button click, or should SM7 offer an automatic prompt when selecting a valid route date that currently has no materialized base rows? | Affects user experience and application behavior. An explicit button avoids unwanted database writes during routine browsing. |
| OQ-003 | If the route template in SM4 is empty for the resolved `HariRuteId` (or if the date is Sunday), what notification should be displayed to the user after triggering materialization? | Affects operational clarity to prevent users from assuming materialization failed. |

# 5. Assumptions

| ID | Assumption |
|----|------------|
| ASM-001 | `IRegenerateVisitPlanWorker` in `btr.application` is the authoritative business logic for materialization and should be reused as-is without introducing duplicated SQL or business rules in the UI. |
| ASM-002 | Materialization triggered from SM7 operates strictly for the selected salesperson (`SalesPersonId = SelectedSalesPersonId`), never for all salespersons globally. |
| ASM-003 | Materialization in SM7 must strictly respect past-date immutability (`AllowPast = false`). Past dates cannot be re-materialized. |
| ASM-004 | Any existing exceptions in `BTR_VisitPlanException` for the selected date must remain untouched and will continue to overlay on top of the newly materialized base plan. |
| ASM-005 | Users interacting with SM7 are authorized supervisors (`LEADR`, `SFKTR`, `SYSAD`). |

# 6. Risks

| ID | Risk | Impact | Mitigation |
|----|------|--------|------------|
| RISK-001 | Overwriting future base plan rows if rolling horizon is chosen | If horizon regeneration runs from `SelectedVisitDate`, any existing future base rows for that salesman are replaced with the current template. | This matches SM4 save behavior; base plan is purely a template projection. Exceptions in `BTR_VisitPlanException` are preserved. |
| RISK-002 | UI responsiveness during materialization | Regenerating a single date takes < 20ms; regenerating 90 days takes ~100–150ms. On high-latency network connections, UI could stutter briefly. | Use wait cursor (`Cursors.WaitCursor`) during execution; execution time for a single salesperson is negligible. |
| RISK-003 | User confusion on Sunday or empty slot | Clicking materialize on Sunday or a day with no route template yields 0 rows, which could look like an error. | Display clear notification indicating the outcome (e.g. "Hari Minggu: tidak ada rute untuk dimaterialisasi" or "Materialisasi selesai: X kunjungan dibuat"). |

# 7. Recommendations

## Option A: Dedicated "Materialisasi Rute" Button for Selected Date Only

Add a dedicated `MaterializeButton` ("Materialisasi Rute") in `TopPanel` of `JadwalKunjunganForm` next to `RefreshButton`.
When clicked:
- Validates that `SelectedVisitDate >= today` and `SelectedVisitDate.DayOfWeek != DayOfWeek.Sunday`.
- Executes `_regenerateVisitPlanWorker.Execute(new RegenerateVisitPlanRequest { SalesPersonId = SelectedSalesPersonId, FromDate = SelectedVisitDate, ToDate = SelectedVisitDate, AllowPast = false, TriggeredBy = "SM7Manual" })`.
- Calls `RefreshPlans()`.
- Shows feedback on result.

### Advantages

- Exactly satisfies the literal phrasing of the issue: "materialize for selected sales person and selected date".
- Minimal execution scope (single date delete/insert).
- Does not alter base plan rows on any other future dates.

### Disadvantages

- If the background worker is not running, browsing to the next day will show empty data again, requiring the user to click materialize day by day.

---

## Option B: Dedicated "Materialisasi Rute" Button with Horizon Option / Default

Add `MaterializeButton` in `TopPanel`. When clicked, it materializes from `SelectedVisitDate` through the rolling horizon (`ToDate = null` / 90 days), or provides a confirmation dialog ("Materialisasi tanggal ini saja" vs "Materialisasi s/d horizon 90 hari").

### Advantages

- Populates the rolling horizon for that salesperson, matching SM4 save behavior.
- Eliminates repeated manual materialization when browsing upcoming dates in the 14-day cycle.
- Aligns with the overall Territory Execution Plan design (`VISIT_PLAN_HORIZON_DAYS`).

### Disadvantages

- Slightly broader write operation (deletes and re-inserts future base plan rows across the horizon for that salesperson).

---

## Option C: Automatic Materialization on Selection / Refresh

Automatically check if `_basePlanRows` is empty when selecting a salesperson and date. If empty and not Sunday, automatically invoke `_regenerateVisitPlanWorker` before loading.

### Advantages

- Fully transparent to the user; no extra button clicks required.

### Disadvantages

- Introduces implicit database write side-effects on read/navigation events (`SelectedIndexChanged`, `ValueChanged`).
- Will repeatedly trigger fruitless write attempts on dates where the template legitimately has 0 assigned customers.
- Contrary to the requested outcome ("Users can trigger visit data materialization directly...").

# 8. Gap Closure

## GAP-001 & GAP-002: In-Menu Materialization Trigger & Worker Injection

### Decision

Inject `IRegenerateVisitPlanWorker` into `JadwalKunjunganForm` and add an explicit `MaterializeButton` ("Materialisasi Rute") on `TopPanel`.

### Rationale

Explicit trigger gives supervisors clear control, avoids unintended background write side-effects during browsing, and directly fulfills the user request. Reusing `IRegenerateVisitPlanWorker` maintains single source of business logic for materialization.

### Impact

Modifies `JadwalKunjunganForm.cs` and `JadwalKunjunganForm.Designer.cs`. No changes required in domain or infrastructure layers.

---

## GAP-003 & OQ-001: Materialization Scope

### Status: CLOSED

### Decision

Materialize for the selected salesperson and selected date (`FromDate = SelectedVisitDate, ToDate = SelectedVisitDate`, `AllowPast = false`, `TriggeredBy = "SM7Manual"`).

### Rationale

Directly satisfies the reporter's requested outcome in the issue ("materialize for selected sales person and selected date"). Minimizes blast radius by isolating data changes to the specific date being inspected and edited in SM7, running near-instantaneously (<20ms). Rolling horizon maintenance remains the responsibility of the background scheduler or SM4 template save.

### Impact

`JadwalKunjunganForm` invokes `_regenerateVisitPlanWorker.Execute` with `FromDate` and `ToDate` set to `SelectedVisitDate`.

### Architecture Impact

None. `RegenerateVisitPlanWorker` already supports date-bounded execution without modification.

## OQ-002: Trigger Modality

### Status: CLOSED

### Decision

Use explicit button click (`MaterializeButton`). Do not perform implicit auto-materialization on selection change.

### Rationale

Prevents unexpected database write operations and performance overhead while merely browsing through dates.

### Impact

Clean UI flow: User selects salesperson, selects date, clicks "Materialisasi Rute" if unmaterialized, and data is loaded into `BasePlanGrid` and `EffectivePlanGrid`.

### Architecture Impact

None.

## OQ-003: User Feedback

### Status: CLOSED

### Decision

- If Sunday: inform that Sunday has no route.
- If past date: inform that past dates cannot be materialized.

### Rationale

Provides transparency and eliminates ambiguity when 0 rows are returned.

# 9. Architecture Applicability

## Decision

**ARCHITECTURE-NOT-REQUIRED**

## Rationale

1. **No new components or architectural boundaries:** The materialization domain aggregate, calendar engine (`IRuteCycleCalendar`), DAL (`IVisitPlanDal`), models (`VisitPlanModel`), and application use case (`IRegenerateVisitPlanWorker`) already exist, are fully implemented, and are registered in DI.
2. **Presentation-only modification:** The required change is confined to injecting `IRegenerateVisitPlanWorker` into `JadwalKunjunganForm` in `btr.distrib` and wiring a button event handler.
3. **No persistence or schema changes:** `BTR_VisitPlan` and `BTR_VisitPlanException` tables and DAL queries remain unchanged.
4. **Existing rules preserved:** Cycle rules, 14-day anchor calculation, past date immutability, and exception overlay resolution remain untouched.
